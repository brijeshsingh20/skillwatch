# Bandwidth estimate (low-bandwidth mode)

Generated by `python -m scripts.bandwidth_report`. One observation every **5 minutes** (12 per hour) per centre. Figures are KB per hour **per centre**, during hours the centre is being monitored.

## Result

| Scenario | KB per hour per centre |
|---|---|
| A. Counts + thumbnail, upload every observation | **145** |
| B. Counts + thumbnail, batch of 6 per upload | **80** |
| C. Counts only (no thumbnail), batch of 6 | **17** |
| D. Worst-case thumbnail (3x larger, real scenes), batch of 6 | **207** |

Headline figure (scenario B, the recommended setting): **about 80 KB per hour per centre**, which is roughly 0.18 kbit/s on average.

## What is sent

- One JSON record per observation (counts, equipment totals, confidence, quality): about 349 bytes.
- One annotated, pixelated thumbnail (224 px wide, JPEG quality 50): about 3.9 KB measured on the demo clips (5.8 KB largest item including base64 and JSON).
- Never video. Never full-resolution frames.

## For comparison (same clips, same machine)

- Uploading the video itself: about **223,207 KB per hour**. This is measured on the synthetic clips; real camera bitrates vary widely with resolution and codec settings.
- One 640 px JPEG every 2 seconds: about **35,570 KB per hour**.

## Assumptions (not measured)

- HTTP headers add about 650 bytes per upload, and each upload opens a fresh TLS connection costing about 6000 bytes.
- Thumbnails of the synthetic scenes compress better than real rooms. Scenario D shows a pessimistic 3x thumbnail size.
- Retries after an outage send each queued item once more, so a backlog costs the same per item as normal operation; items already received are never re-sent.
- The edge box does the analysis locally, so analysis time above is CPU on the centre's machine, not bandwidth.
